1. Purpose of this document

This document explains, in simple language:

  • What white label means for PrepCorex
  • The two models: Subscription and Agency
  • Every major client, admin, and warehouse feature today
  • How partner accounts are created and set up
  • Why partners cannot use our .env secrets — and how each service must be set up for them
  • How marketplace integrations work end-to-end (connect + process orders)
  • Problems with partner domains and the options to fix them
  • A build plan you can approve before development starts
Today’s truth: PrepCorex is one branded product (one domain, one Stripe, one Drive, one set of env secrets). White label is not built yet. Feature on/off per user already exists and is a strong base for partner “feature packs.”

2. What white label means (simple)

White label = the same PrepCorex engine, but the partner’s clients see the partner’s company — name, logo, colors, emails, invoices — on the partner’s own domain (for example app.partnercompany.com), not PrepCorex.

PrepCorex / Prep Services FBA remains the platform owner. Partners get a branded space. They do not get the source code.

Shared rule for both models: partners always use their own domain. PrepCorex.com stays the master PSF product only.

4. Feature packs (admin decides what the partner gets)

PrepCorex admin turns modules on or off for each partner organization.

Example: if Warehouse Ops is off, that partner’s system behaves like PrepCorex before the floor app existed (client requests + admin oversight, no receive/pick/pack phone app).

Partner admins can only grant their users features that sit inside the pack PrepCorex allowed. They cannot unlock Buy Labels or Shopify if the pack turned those off.

9. How a white-label account is created and set up

Recommended first version: PrepCorex super-admin creates every partner (not full self-serve).

  1. Create organization — company name, model (Subscription / Agency), owner email, status Draft.
  2. Domain — partner domain (required). Partner points DNS (CNAME) to PrepCorex hosting. Admin marks domain verified when HTTPS works.
  3. Branding — logo, app name, colors, favicon, email from-name.
  4. Feature pack — which modules are allowed (including Warehouse Ops on/off).
  5. Partner admin user — created and linked to that organization.
  6. Connections — partner (or PrepCorex for Agency) completes Connect flows: Stripe, email/SMTP, Drive, carriers if needed, marketplaces (see sections 10–12).
  7. People — partner invites staff and clients. Agency: assign PrepCorex operators to the org.
  8. Go live — status Active. Clients only use the partner domain.
Critical design rule: everything that today lives in server .env for PrepCorex must become either (a) platform-managed for that partner during provisioning, or (b) a Connect / Settings screen that stores secrets in the database for that organization. Partners never SSH into Vercel and never edit .env.

10. The “no .env” problem (most important technical truth)

PrepCorex today is configured mostly like this:

  • One Vercel project
  • One Firebase project
  • One Stripe account
  • One Google Drive OAuth app + one connected Drive
  • One SMTP mailbox
  • One Shippo / ShipBest / GOFO carrier setup
  • One LiveKit project
  • One Shopify / eBay / Amazon / TikTok / Etsy developer app each
  • Secrets in environment variables

White-label partners have no access to those env files. So we must split every secret into one of three buckets:

Bucket Meaning Examples
A. Partner Connect in UI Partner clicks Connect or pastes keys in Settings. Stored encrypted per organization. Stripe Connect; Google Drive Connect; SMTP settings; WooCommerce / ShipStation / Veeqo keys (already per-user); marketplace “Connect store”
B. PrepCorex provisions Our team configures once when creating the partner. Partner never sees the raw secret. Domain DNS + SSL; Firebase project or tenant id; LiveKit keys; marketplace developer apps; cron secrets
C. Shared platform (optional) PrepCorex keeps one account and resells / operates it for partners (especially Agency). Shared Shippo with markup; shared OpenAI for LEXI; shared CRM bridge

12. Marketplace integrations — how they work (connect + process)

Integrations are not finished when the store is “Connected.” Full lifecycle:

  1. Connect — OAuth or API keys → tokens saved for that user/shop.
  2. Select / map products — link marketplace SKUs to PrepCorex inventory.
  3. Receive orders — webhooks and/or polling sync orders into PrepCorex.
  4. Warehouse process — pick / pack / dispatch (or admin fulfill if Ops pack is off).
  5. Push back — mark fulfilled + send tracking to the marketplace.
  6. Inventory sync — push/pull quantities where supported.

13. Integrations + own domain — problems and options

When the partner uses app.partner.com, every OAuth redirect and many webhooks must match that host (or a deliberate shared host). Platforms reject mismatched URLs.

13.1 Problems

  • OAuth redirect URI must be pre-registered (Shopify, eBay, Amazon, TikTok, Etsy, Google, Azure).
  • Webhooks must hit a public HTTPS URL Shopify/TikTok/etc. can call.
  • One shared env app cannot magically know 50 partner domains unless we register all domains or use a shared callback host.
  • eBay RuName is especially domain-sensitive (we already have a partial EBAY_RUNAME_BY_HOST pattern).
  • Firebase Auth authorized domains must include every partner host.
  • Email verification / password reset links must not send users back to prepcorex.com.
  • “Invalid webhook URL” style failures appear if a store was connected with a bad/old URL (already seen on Shopify logs for some shops).

13.2 Options to resolve

OptionHow it worksProsCons
A. Shared integrations host
(recommended v1)		 UI stays on partner domain. OAuth + webhooks use stable integrations.prepcorex.com (or similar), then return user to partner domain. One app registration; fewer portal reviews; faster onboarding Brief non-partner host during connect; must explain to partners
B. Per-partner domain callbacks Every partner domain is added as redirect/webhook on the same developer apps, or each partner gets their own developer apps. Fully on partner brand/domain Heavy ops; some platforms limit redirects; more secrets
C. Hybrid A for most partners; B for large partners who require it. Practical Two paths to maintain
Recommendation to finalize: Option A (shared integrations host) for v1, while the partner product UI always stays on their domain. Document this clearly in partner contracts.

15. Recommended build plan (phases)

  1. Phase 0 — Decisions — Approve models, domain rule, integrations Option A/B/C, carrier Option 1/2, Agency access levels, legal approach.
  2. Phase 1 — Organizations — Firestore organizations, link users, migrate current PrepCorex into master org.
  3. Phase 2 — Domain routing — Host → org; auth links; Firebase authorized domains process.
  4. Phase 3 — Branding — Logo, name, colors, emails, hide PrepCorex marketing on partner hosts.
  5. Phase 4 — Org feature packs — Enforce pack in UI + APIs; Warehouse Ops off = pre-ops behavior.
  6. Phase 5 — Stripe Connect — Partner Connect; invoice + Buy Labels charges to partner account.
  7. Phase 6 — Partner Settings Connectors — SMTP, Google Drive, (optional) carrier keys; no .env for partners.
  8. Phase 7 — Agency co-manage — Assign PrepCorex staff into agency orgs; audit log.
  9. Phase 8 — Integrations host — Shared OAuth/webhook host + reconnect tooling for existing shops.
  10. Phase 9 — Pilot — One Subscription + one Agency fake/real partner; runbook; go-live checklist.

18. Bottom line

Product: Two models (Subscription & Agency), always on the partner’s domain, with admin-controlled feature packs.

Already strong: Per-user feature flags and most client/admin/ops modules.

Must build: Organizations, domain routing, branding, org packs, Stripe Connect, partner Settings connectors (because partners have no .env), Agency co-manage, and an integrations domain strategy so order processing webhooks keep working.

Do not confuse: Connecting a store is only step one. White label must also keep order sync, fulfill, inventory sync, and webhooks healthy on the partner’s commercial domain plan.
